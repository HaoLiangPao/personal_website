# 写 spec

```markdown
## 角色与背景
你是 <项目> 的 <角色>。项目一句话：…… 先读：<文件列表>

## 目标
要交付什么，为什么要做。

## 边界
- 可改：<路径>
- 绝对不可改：<路径>
- 依赖：能否安装  / commit：能否提交

## 精确接口
要调用的函数和 API 的完整签名。

## 已知的坑
你知道而它不知道的陷阱。

## 验收标准（逐条可执行）
1. <命令> → <预期>
2. <用户流程> → <可观察的结果>
自己全部跑过再汇报。

## 汇报
文件清单、spec 之外的自主决定、验证证据、未验证项。
```

## 派活前检查
- [ ] 边界写了吗？这是最容易省略、也最容易出事的一项。
- [ ] 跨层功能的验收标准，是否跑到用户最终看到结果的那一步？
- [ ] 需要的工具（浏览器、凭证、外部 API）预检过吗？
- [ ] 模型选对了吗？判断用贵的，实现用中等的，搬运用便宜的。
- [ ] 并行任务的文件是否互不重叠？
